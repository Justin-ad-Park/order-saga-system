# 12-1. 동시성 이슈 다이어그램

## 시나리오
OrderOrchestrator가 쿠폰 예약을 요청했는데 네트워크 지연/타임아웃으로 예약 응답이 늦게 도착하고, 그 사이 보상(compensate)이 먼저 처리되는 케이스를 예로 든다.

## 동시성 충돌 타임라인 (문제 상황)
```
시간
  |  OrderOrchestrator           CouponService              Outbox/Consumer
  |
  |  reserve 요청 ──────────────>  (지연/timeout)  ────────
  |  (오케스트레이터는 실패로 판단)                             |
  |  compensate 이벤트 발행 ─────────────────────────────── | ──────>     
  |                             compensate 처리   <────── | ──────
  |                             (예약 취소/복구 수행)        |
  |                             쿠폰 상태: AVAILABLE       |
  |                           (뒤늦게 예약 처리 완료) <────────
  |                             reserve 처리
  |                             쿠폰 상태: RESERVED  (문제)
  |
```

- 보상(compensate)이 먼저 수행되었는데, 뒤늦게 예약(reserve)이 성공 처리되어 상태가 뒤집히는 문제가 발생한다.

## 해결 전략: coupon_reservation 상태 기록
핵심은 `coupon_reservation` 테이블에 **order_id 기준의 예약/보상 상태를 기록**해, 순서가 뒤바뀌어도 일관되게 처리하는 것이다.

### 적용 규칙
- 예약 요청 시
  - 먼저 `coupon_reservation`에 `RESERVED` 기록
  - 이미 `CANCELLED`가 기록되어 있으면 예약을 무시
- 보상 요청 시
  - `coupon_reservation`에 `CANCELLED` 기록
  - 이후 예약 요청이 와도 `CANCELLED`면 무시

## 동시성 충돌 타임라인 (해결 이후)
```
시간
  |  OrderOrchestrator           CouponService              coupon_reservation
  |
  |  reserve 요청 ──────────────>  (지연/timeout) ────────────────
  |  (오케스트레이터는 실패로 판단)                                    |
  |  compensate 이벤트 발행 ───────────────────────────────>       |
  |                             compensate 처리                   |
  |                             reservation: CANCELLED 저장       |
  |                                   (뒤늦게 예약 처리 시도) <───────
  |                             reserve() 처리
  |                               -reservation 상태 확인
  |                               -CANCELLED -> 예약 무시
  |                             쿠폰 상태: AVAILABLE 유지
  |
```

## 요약
- 순서 역전이 발생하더라도 `coupon_reservation` 상태가 최종 판단 기준이 된다.
- 예약/보상이 **멱등적**으로 처리되며, 타이밍 이슈가 사가 보상 흐름에 영향을 주지 않는다.
